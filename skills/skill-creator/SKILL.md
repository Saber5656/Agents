# スキルクリエイター

新しいスキルを作成し、テスト・ベンチマークまで完了させるためのスキル。既存スキルを修正する場合は `skill-updater` を使う。

スキル作成の大まかな流れ：

- スキルに何をさせたいか、どのように動作させるかを決める
- スキルのドラフトを作成する
- テストプロンプトをいくつか作成し、そのスキルにアクセスした状態のClaudeで実行する。テストは必須であり、省略しない
- 定性的・定量的にユーザーが結果を評価できるようサポートする
  - 実行が進む間、定量的なevalがなければ下書きする（あれば、そのまま使うか修正するか検討する）。ユーザーに説明する（または既存のものであれば、それを説明する）
  - `eval-viewer/generate_review.py` スクリプトを使ってユーザーが結果を確認できるようにし、定量メトリクスも見られるようにする
- ユーザーの評価フィードバックと定量ベンチマークから明らかな問題点をもとにスキルを書き直す
- 満足するまで繰り返す
- テストセットを拡大して、より大規模にやり直す

このスキルを使う際の役割は、ユーザーがこのプロセスのどこにいるかを把握し、次のステージへ進めることを支援すること。例えば「Xのスキルを作りたい」と言ってきたら、意図を明確にし、ドラフトを書き、テストケースを考え、評価方法を決め、プロンプトを全部実行し、繰り返す。

一方、すでにスキルのドラフトがある場合は、eval/反復の部分から始めればよい。

テストを省略してよい、感覚でよい、あとでよいと言われても、新規スキル作成では最低限の eval / benchmark を必ず実施する。規模は小さくしてよいが、テストなしで完了宣言しない。

スキルが完成したら（順序は柔軟）、専用スクリプトを使ってスキルのdescription最適化を実行し、トリガー精度を向上させることもできる。

## この環境の配置規約

- スキルの実体は `~/dev/skills/<skill-name>/` に作成・編集する
- `~/.claude/skills` と `~/.codex/skills` は `~/dev/skills` へのシンボリックリンクとして扱う
- 新規スキルは `~/.claude/skills/` や `~/.codex/skills/` のリンク先ではなく、実体の `~/dev/skills/` 配下に置く
- ルートの startup instructions にスキル配置規約を重複して書かないこと。このスキルがその責務を持つ

## ユーザーとのコミュニケーション

スキルクリエイターは、コーディング用語への親しみが幅広いユーザーに使われる可能性がある。最近、Claudeのパワーに触発されてターミナルを開く配管工や、「npmのインストール方法」をGoogle検索する親御さんや祖父母が増えているという傾向がある。一方で、ユーザーの大半はコンピューターに比較的詳しい人たちだろう。

コンテキストの手がかりに注意して、どのように言葉を選ぶか判断してほしい。デフォルトのケースでは：

- 「evaluation（評価）」と「benchmark（ベンチマーク）」はギリギリだが、OK
- 「JSON」や「assertion（アサーション）」はユーザーがそれを理解していることを示す明確なサインが見られてから、説明なしに使う

疑わしいときは用語を簡単に説明するのはOK。ユーザーが理解できるか自信がない場合は、短い定義で補足して構わない。

## スキルの作成

### 意図の把握

まずユーザーの意図を理解する。現在の会話に、ユーザーがスキルとして保存したいワークフローがすでに含まれている場合もある（例：「これをスキルにして」）。その場合は、会話履歴から先に答えを抽出する — 使用したツール、ステップの順序、ユーザーが行った修正、確認された入出力フォーマット。不足部分はユーザーに補完してもらい、次のステップに進む前に確認すること。

1. このスキルはClaudeに何を可能にすべきか？
2. このスキルはいつトリガーされるべきか？（どのユーザーフレーズ／コンテキストで）
3. 期待される出力フォーマットは何か？
4. スキルが正しく動作することを検証するテストケースをどう設計するか？客観的に検証可能な出力（ファイル変換、データ抽出、コード生成、固定ワークフローステップ）を持つスキルはもちろん、主観的な出力（文体、アート）でも定性的レビュー用の eval を作る。新規スキル作成ではテストなしで完了宣言しない。

### インタビューとリサーチ

エッジケース、入出力フォーマット、サンプルファイル、成功基準、依存関係について積極的に質問する。この部分が固まるまでテストプロンプトを書くのは待つこと。

利用可能なMCPを確認する — リサーチに役立つ場合（ドキュメント検索、類似スキルの発見、ベストプラクティスの調査）、サブエージェントが使えれば並列でリサーチし、なければインラインで実施。ユーザーの負担を減らすため、事前にコンテキストを準備して臨む。

### SKILL.md の作成

スキルファイルのフォーマット・フロントマターフィールド・テンプレートは `../TEMPLATE.md`（skills ディレクトリ直下）を参照すること。テンプレート（ユーザー呼び出し / 自動トリガー / 複合ワークフロー）と必須フィールドの一覧が記載されている。

ユーザーインタビューをもとに、以下のコンポーネントを埋める：

- **name**: スキルの識別子
- **description**: トリガーのタイミングと機能。これがトリガーの主要メカニズム — スキルが何をするかと、いつ使うべきかという具体的なコンテキストの両方を含める。「いつ使うか」の情報はすべてここに書き、本文には書かない。注：現在Claudeはスキルを「アンダートリガー」する傾向がある（有用な場面でも使わないこと）。これを防ぐため、descriptionは少し「押しの強い」書き方にする。例えば「内部Anthropicデータを表示するシンプルで速いダッシュボードの作り方」ではなく「内部Anthropicデータを表示するシンプルで速いダッシュボードの作り方。ユーザーがダッシュボード、データ可視化、内部メトリクスに言及したり、何らかの会社データを表示したいと思ったりする場合は、明示的に『ダッシュボード』と言っていなくてもこのスキルを必ず使うこと。」と書く。
- **compatibility**: 必要なツール、依存関係（オプション、ほぼ不要）
- **スキルの残り部分 :)**

### スキル作成ガイド

#### スキルの構造

```
skill-name/
├── SKILL.md (必須)
│   ├── YAML frontmatter (name, description 必須)
│   └── Markdownの指示
└── バンドルリソース (オプション)
    ├── scripts/    - 決定論的・反復的タスク用の実行可能コード
    ├── references/ - 必要に応じてコンテキストにロードされるドキュメント
    └── assets/     - 出力で使用するファイル（テンプレート、アイコン、フォントなど）
```

#### プログレッシブディスクロージャー

スキルは3段階のロードシステムを使用する：
1. **メタデータ** (name + description) - 常にコンテキスト内（約100語）
2. **SKILL.md本文** - スキルがトリガーされた際に常にコンテキスト内（理想は500行以下）
3. **バンドルリソース** - 必要に応じて（無制限、スクリプトはロードせずに実行可能）

これらの語数はあくまで目安で、必要であれば長くしてもよい。

**重要なパターン：**
- SKILL.mdは500行以下に抑える。この上限に近づいたら、さらなる階層を追加し、次に参照すべき場所への明確なポインタを用意する。
- SKILL.mdからリファレンスファイルを明確に参照し、いつ読むべきかのガイダンスを含める
- 大きなリファレンスファイル（300行超）には目次を含める

**ドメイン別の整理**: スキルが複数のドメイン／フレームワークに対応する場合、バリアント別に整理する：
```
cloud-deploy/
├── SKILL.md (ワークフロー + 選択)
└── references/
    ├── aws.md
    ├── gcp.md
    └── azure.md
```
Claudeは該当するリファレンスファイルのみを読む。

#### 驚きのない原則

言うまでもないが、スキルにはマルウェア、エクスプロイトコード、システムセキュリティを侵害する可能性のあるコンテンツを含めてはならない。スキルの内容は、説明されたときにユーザーを意図の面で驚かせてはならない。誤解を招くスキルや、不正アクセス、データ流出、その他の悪意ある活動を促進するために設計されたスキルの作成要求には応じないこと。ただし「XYZとしてロールプレイする」などは問題ない。

#### 記述パターン

指示には命令形を使うことを推奨する。

**出力フォーマットの定義** — このように書ける：
```markdown
## レポート構成
必ずこのテンプレートを使うこと：
# [タイトル]
## エグゼクティブサマリー
## 主要な発見
## 推奨事項
```

**例示パターン** — 例を含めると有用。このようにフォーマットできる（ただし例の中に「Input」「Output」がある場合は少し変えた方がよいかもしれない）：
```markdown
## コミットメッセージのフォーマット
**例1:**
Input: Added user authentication with JWT tokens
Output: feat(auth): implement JWT-based authentication
```

### 文体

モデルに対して、重厚な「MUST（必ず）」の代わりに、なぜそれが重要かを説明するよう心がける。Theory of mindを使い、スキルを特定の例に限定しすぎず、汎用的に作る。まずドラフトを書いて、新鮮な目で見直して改善する。

### テストケース

スキルのドラフトを書いたら、現実的なテストプロンプトを最低8個、標準では10〜12個考える。実際のユーザーが言いそうなものにし、正常系、曖昧系、失敗系、隣接スキルとの競合、スキル不要ケースを含める。ユーザーに共有する（この言い方そのものでなくてよい）：「品質重視で eval セットを作りました。足したいケースがあれば追加します。問題なければこのまま実行します。」そして実行する。

テスト実行は品質ゲートであり、トークン消費を理由に省略しない。ユーザーが「軽くでよい」と言った場合でも、最低限の eval、採点、benchmark、レビュー可能な成果物を残してから完了する。

テストケースは `evals/evals.json` に保存する。アサーションはまだ書かない — プロンプトだけ。アサーションは実行中に次のステップで下書きする。

```json
{
  "skill_name": "example-skill",
  "evals": [
    {
      "id": 1,
      "prompt": "ユーザーのタスクプロンプト",
      "expected_output": "期待される結果の説明",
      "files": []
    }
  ]
}
```

完全なスキーマ（後で追加する `assertions` フィールドを含む）は `references/schemas.md` を参照。

## テストケースの実行と評価

このセクションは一連の流れ — 途中で止めないこと。`/skill-test` や他のテストスキルは使わないこと。

結果は `skills/.workspace/<skill-name>/` に置く（スキルディレクトリ直下ではなく、skills ルートの `.workspace/` 配下）。ワークスペース内では、イテレーション別（`iteration-1/`、`iteration-2/` など）に整理し、その中で各テストケースがディレクトリを持つ（`eval-0/`、`eval-1/` など）。最初から全部作らず、必要になったら都度作成する。

### ステップ1：同じターンで全実行を起動（スキルあり・ベースライン両方）

各テストケースについて、同じターンで2つのサブエージェントを起動する — 1つはスキルあり、1つはなし。これは重要：スキルありの実行を先に起動してベースラインを後回しにしてはならない。全部を一度に起動し、ほぼ同時に終わるようにする。

**スキルあり実行：**

```
このタスクを実行してください：
- スキルパス: <path-to-skill>
- タスク: <eval プロンプト>
- 入力ファイル: <evalファイルがあれば、なければ "none">
- 出力先: <workspace>/iteration-<N>/eval-<ID>/with_skill/outputs/
- 保存する出力: <ユーザーが重視するもの — 例：".docxファイル"、"最終CSV">
```

**ベースライン実行**（同じプロンプトだが、ベースラインはコンテキストに依存）：
- **新規スキル作成時**: スキルなし。同じプロンプト、スキルパスなし、`without_skill/outputs/` に保存。
- **既存スキルの改善時**: 旧バージョン。編集前にスキルをスナップショット（`cp -r <skill-path> <workspace>/skill-snapshot/`）し、ベースラインサブエージェントをそのスナップショットに向ける。`old_skill/outputs/` に保存。

各テストケースに `eval_metadata.json` を作成する（アサーションは今は空でよい）。各evalにはテストしている内容を示す説明的な名前をつける — 「eval-0」だけではなく。この名前をディレクトリ名にも使う。このイテレーションで新規または変更されたevalプロンプトを使う場合、各新規evalディレクトリにこのファイルを作成する — 前のイテレーションから引き継がれると思わないこと。

```json
{
  "eval_id": 0,
  "eval_name": "説明的な名前",
  "prompt": "ユーザーのタスクプロンプト",
  "assertions": []
}
```

### ステップ2：実行中にアサーションを下書きする

実行が終わるのをただ待つのではなく — この時間を有効活用できる。各テストケースの定量的なアサーションを下書きし、ユーザーに説明する。`evals/evals.json` にアサーションがすでにある場合は、それを確認して何をチェックするか説明する。

良いアサーションは客観的に検証可能で説明的な名前を持つ — ベンチマークビューアで結果を一見したときに、各アサーションが何をチェックするかがすぐに分かるように読める。主観的なスキル（文体、デザイン品質）は定性的に評価した方がよい — 人間の判断が必要なものに無理にアサーションをつけないこと。

アサーションが下書きできたら `eval_metadata.json` ファイルと `evals/evals.json` を更新する。ユーザーがビューアで何を見るか — 定性的な出力と定量ベンチマークの両方 — も説明する。

### ステップ3：実行が完了したらタイミングデータを記録する

各サブエージェントタスクが完了すると、`total_tokens` と `duration_ms` を含む通知を受け取る。このデータを即座に実行ディレクトリの `timing.json` に保存する：

```json
{
  "total_tokens": 84852,
  "duration_ms": 23332,
  "total_duration_seconds": 23.3
}
```

このデータをキャプチャできる唯一の機会 — タスク通知を通じて届き、それ以外には永続化されない。バッチにしようとせず、通知が届いたらその都度処理すること。

### ステップ4：採点、集計、ビューアの起動

全実行が完了したら：

1. **各実行を採点する** — グレーダーサブエージェントを起動（またはインラインで採点）し、`agents/grader.md` を読んで各アサーションを出力に対して評価する。結果を各実行ディレクトリの `grading.json` に保存する。grading.jsonのexpectations配列は `text`、`passed`、`evidence` フィールドを使うこと（`name`/`met`/`details` などの変形は使わない）— ビューアはこの正確なフィールド名に依存している。プログラムで確認できるアサーションは、目視ではなくスクリプトを書いて実行する — スクリプトの方が速く、信頼性が高く、イテレーション間で再利用できる。

2. **ベンチマークに集計する** — skill-creatorディレクトリから集計スクリプトを実行する：
   ```bash
   python -m scripts.aggregate_benchmark <workspace>/iteration-N --skill-name <name>
   ```
   これにより、各設定のpass_rate、time、tokensをmean ± stddevとdeltaで示した `benchmark.json` と `benchmark.md` が生成される。benchmark.jsonを手動で生成する場合は、ビューアが期待する正確なスキーマについて `references/schemas.md` を参照すること。
   with_skillバージョンをベースラインの前に配置すること。

3. **アナリストパスを実施する** — ベンチマークデータを読んで、集計統計が隠してしまうパターンを浮き上がらせる。何を探すか — スキルに関わらず常にpassするアサーション（識別力がない）、高分散のevals（おそらく不安定）、time/tokenのトレードオフ — については `agents/analyzer.md`（「ベンチマーク結果の分析」セクション）を参照すること。

4. **ビューアを起動する** — 定性的な出力と定量的なデータの両方で：
   ```bash
   nohup python <skill-creator-path>/eval-viewer/generate_review.py \
     <workspace>/iteration-N \
     --skill-name "my-skill" \
     --benchmark <workspace>/iteration-N/benchmark.json \
     > /dev/null 2>&1 &
   VIEWER_PID=$!
   ```
   イテレーション2以降では `--previous-workspace <workspace>/iteration-<N-1>` も渡す。

   **Cowork / ヘッドレス環境：** `webbrowser.open()` が利用不可またはディスプレイがない環境では、サーバーを起動する代わりに `--static <output_path>` を使ってスタンドアロンHTMLファイルを書き出す。ユーザーが「すべてのレビューを送信」をクリックすると、フィードバックが `feedback.json` ファイルとしてダウンロードされる。ダウンロード後、次のイテレーションが読み取れるよう `feedback.json` をワークスペースディレクトリにコピーする。

   注：ビューアの作成には generate_review.py を使うこと。カスタムHTMLを書く必要はない。

5. **ユーザーに伝える** — 例：「ブラウザで結果を開きました。タブが2つあります — 『Outputs』では各テストケースをクリックしてフィードバックを残せます。『Benchmark』では定量的な比較が表示されます。終わったら戻ってきて教えてください。」

### ビューアでユーザーが見るもの

「Outputs」タブでは一度に1つのテストケースを表示：
- **Prompt**: 与えられたタスク
- **Output**: スキルが生成したファイル（可能な場合はインラインでレンダリング）
- **Previous Output**（イテレーション2以降）: 前回の出力を折りたたんで表示するセクション
- **Formal Grades**（採点が実行されている場合）: アサーションのpass/failを折りたたんで表示するセクション
- **Feedback**: 入力しながら自動保存されるテキストボックス
- **Previous Feedback**（イテレーション2以降）: 前回のコメントをテキストボックスの下に表示

「Benchmark」タブでは統計サマリーを表示：各設定のpass rate、タイミング、トークン使用量をeval別の内訳とアナリストの観察とともに表示。

ナビゲーションは前へ/次へボタンまたは矢印キー。完了したら「すべてのレビューを送信」をクリックし、全フィードバックが `feedback.json` に保存される。

### ステップ5：フィードバックを読む

ユーザーが完了を伝えてきたら、`feedback.json` を読む：

```json
{
  "reviews": [
    {"run_id": "eval-0-with_skill", "feedback": "グラフに軸のラベルがない", "timestamp": "..."},
    {"run_id": "eval-1-with_skill", "feedback": "", "timestamp": "..."},
    {"run_id": "eval-2-with_skill", "feedback": "完璧、これが好き", "timestamp": "..."}
  ],
  "status": "complete"
}
```

空のフィードバックはユーザーが問題ないと思ったことを意味する。ユーザーが具体的な不満を持ったテストケースに改善を集中させる。

完了したらビューアサーバーを停止する：

```bash
kill $VIEWER_PID 2>/dev/null
```

## スキルの改善

これがループの核心。テストケースを実行し、ユーザーが結果を確認し、フィードバックをもとにスキルをより良くする。

### 改善の考え方

1. **フィードバックから一般化する。** ここで起きていることの大局として、私たちは何百万回（もしかしたら文字通り、あるいはそれ以上）も多様なプロンプトで使えるスキルを作ろうとしている。ユーザーとは同じ例を繰り返し反復しているが、それは速く進むためだ。ユーザーはこれらの例を熟知していて、新しい出力を素早く評価できる。しかし、ユーザーと共同開発しているスキルがその例にしか機能しないなら無意味だ。細かく過学習した変更や、過度に制約的なMUSTを入れる代わりに、頑固な問題があれば、別の比喩を使ったり、別の作業パターンを推奨したりしてみる。試すコストは比較的低く、素晴らしいものが見つかるかもしれない。

2. **プロンプトをスリムに保つ。** 役に立っていないものは削除する。最終出力だけでなくトランスクリプトを必ず読む — スキルがモデルに生産的でないことに多くの時間を費やさせているようであれば、そうさせているスキルの部分を削除してみて何が起きるか確認する。

3. **理由を説明する。** モデルに求めていることすべての**理由**を懸命に説明する。今日のLLMは*賢い*。良いハーネスを与えられると、機械的な指示を超えて、本当に物事を実現できる。ユーザーのフィードバックが簡潔だったりフラストレーションを感じさせるものであっても、タスクとユーザーがなぜそれを書いたのか、何を書いたのかを実際に理解しようとし、その理解を指示に伝えること。ALWAYSやNEVERを大文字で書いたり、超硬直した構造を使い始めたりしたら、それは黄色信号 — 可能であれば、なぜそれが重要なのかを説明するようにアプローチを再構成する。それがより人道的で、強力で、効果的なアプローチだ。

4. **テストケース間の繰り返し作業を探す。** テスト実行のトランスクリプトを読んで、サブエージェントが全員独立して似たようなヘルパースクリプトを書いたり、何かに対して同じ複数ステップのアプローチを取ったりしていないか確認する。3つのテストケース全てで、サブエージェントが `create_docx.py` や `build_chart.py` を書いていたなら、スキルがそのスクリプトをバンドルすべき強いシグナルだ。一度書いて `scripts/` に置き、スキルにそれを使うよう指示する。これにより将来のすべての呼び出しがゼロから作り直す手間を省ける。

このタスクはかなり重要で、あなたの思考時間はボトルネックではない。時間をかけてじっくり考えること。ドラフトの改訂版を書いて、新鮮な目で見直して改善することを勧める。ユーザーの頭の中に入り込み、何を望み何を必要としているかを本当に理解するよう最善を尽くして。

### 反復ループ

スキルを改善した後：

1. スキルに改善を適用する
2. 新しい `iteration-<N+1>/` ディレクトリに全テストケースを再実行する（ベースライン実行を含む）。新規スキル作成時はベースラインは常に `without_skill`（スキルなし）— これはイテレーション間で変わらない。既存スキルの改善時は、何がベースラインとして意味があるか判断する：ユーザーが持ち込んだ元のバージョンか、前のイテレーションか。
3. `--previous-workspace` を前のイテレーションに向けてレビュアーを起動する
4. ユーザーがレビューして完了を伝えるのを待つ
5. 新しいフィードバックを読み、また改善して繰り返す

以下のいずれかになるまで続ける：
- ユーザーが満足したと言う
- フィードバックが全て空（全部良く見える）
- 意味のある進歩が得られていない

## 上級：ブラインド比較

2つのバージョンのスキルをより厳密に比較したい場合（例：「新バージョンは本当に良くなったか？」）、ブラインド比較システムがある。詳細は `agents/comparator.md` と `agents/analyzer.md` を読む。基本的なアイデアは：どちらのスキルが生成したかを教えずに2つの出力を独立したエージェントに渡して品質を判定させる。その後、勝者が勝った理由を分析する。

これはオプションで、サブエージェントが必要で、ほとんどのユーザーには不要。人間のレビューループで通常は十分。

## description の最適化

SKILL.md frontmatterのdescriptionフィールドは、エージェントがスキルを使うべきか判断する主要メカニズム。スキルを作成または改善した後、Codex routing eval で description の最適化を提案する。この eval は Claude Code の live trigger 観測ではなく、Codex が name + description + query を見て `should_use_skill` を判定する品質テストである。

### ステップ1：トリガーevalクエリの生成

24個以上のevalクエリを作成する — 使うべきものと使うべきでないものの混合。JSONで保存：

```json
[
  {"query": "ユーザーのプロンプト", "should_trigger": true},
  {"query": "別のプロンプト", "should_trigger": false}
]
```

クエリはリアルで、Claude CodeまたはClaude.aiのユーザーが実際に入力するようなものでなければならない。抽象的な要求ではなく、具体的で詳細なもの。例えば、ファイルパス、ユーザーの仕事や状況についての個人的なコンテキスト、カラム名と値、会社名、URL。少しの背景説明。小文字や略語、タイポ、カジュアルな表現を含むものもある。長さのバリエーションを使い、明確なものよりもエッジケースに焦点を当てる（ユーザーがサインオフする機会がある）。

悪い例：`"このデータをフォーマットして"`、`"PDFからテキストを抽出して"`、`"グラフを作って"`

良い例：`"うちのボスがxlsxファイルを送ってきたんだけど（ダウンロードにあって、'Q4 sales final FINAL v2.xlsx'みたいな名前）、利益率をパーセントで示す列を追加してほしいって。売上はC列でコストはD列だったと思う"`

**should-triggerクエリ**（最低12個）では、カバレッジを考える。同じ意図の異なる表現 — フォーマルなものもカジュアルなものも。ユーザーがスキルやファイルタイプを明示的に名指しせずにも明らかに必要としているケースを含める。あまり使われないユースケースや、このスキルが別のスキルと競合するが勝つべきケースも入れる。

**should-not-triggerクエリ**（最低12個）では、最も価値が高いのはニアミス — スキルとキーワードやコンセプトを共有するが実際には別のものが必要なクエリ。隣接ドメイン、単純なキーワードマッチングでトリガーされてしまうが本当はすべきでない曖昧な表現、スキルが関連する何かに触れるが別のツールがより適切なコンテキストを考える。

避けるべき重要な点：should-not-triggerクエリを明らかに無関係にしないこと。PDFスキルのネガティブテストとして「フィボナッチ関数を書いて」は簡単すぎる — 何もテストしない。ネガティブケースは本当にトリッキーなものにすること。

### ステップ2：ユーザーとのレビュー

HTMLテンプレートを使ってevalセットをユーザーにレビューしてもらう：

1. `assets/eval_review.html` からテンプレートを読む
2. プレースホルダーを置き換える：
   - `__EVAL_DATA_PLACEHOLDER__` → evalアイテムのJSON配列（引用符なし — JS変数代入）
   - `__SKILL_NAME_PLACEHOLDER__` → スキルの名前
   - `__SKILL_DESCRIPTION_PLACEHOLDER__` → スキルの現在のdescription
3. 一時ファイルに書き出す（例：`/tmp/eval_review_<skill-name>.html`）して開く：`open /tmp/eval_review_<skill-name>.html`
4. ユーザーはクエリを編集し、should-triggerを切り替え、エントリを追加/削除して「Export Eval Set」をクリックできる
5. ファイルは `~/Downloads/eval_set.json` にダウンロードされる — 複数ある場合（例：`eval_set (1).json`）は最新バージョンをDownloadsフォルダで確認すること

このステップは重要 — 悪いevalクエリは悪いdescriptionにつながる。

### ステップ3：最適化ループの実行

ユーザーに伝える：「時間がかかります — バックグラウンドで最適化ループを実行し、定期的に確認します。」

evalセットをワークスペースに保存してからバックグラウンドで実行する：

```bash
python -m scripts.run_loop \
  --eval-set <path-to-trigger-eval.json> \
  --skill-path <path-to-skill> \
  --routing-model <model-id-powering-this-session> \
  --improvement-model <model-id-powering-this-session> \
  --max-iterations 7 \
  --runs-per-query 3 \
  --num-workers 6 \
  --timeout 60 \
  --verbose
```

システムプロンプトのモデルID（現在のセッションを動かしているもの）を使うことで、Codex routing eval がユーザーが実際に体験するモデルに近くなる。

実行中は、定期的に出力をtailして、どのイテレーションにいてスコアがどうか、ユーザーに更新情報を提供する。

これにより完全な最適化ループが自動的に処理される。evalセットをトレーニング60%とホールドアウトテスト40%に分割し、現在のdescriptionを評価し（信頼性の高い routing rate を得るため各クエリを3回実行）、失敗したものをもとに Codex が改善案を提案する。各新しいdescriptionをトレーニングとテストの両方で再評価し、最大7回反復する。完了すると、イテレーションごとの結果を示すHTMLレポートをブラウザで開き、`best_description` を持つJSONを返す — 過学習を避けるためトレーニングスコアではなくテストスコアで選択。

`codex exec` の実行失敗、timeout、構造化出力 parse 失敗は、negative eval の成功として扱わない。品質ゲート用途ではインフラ失敗を hard fail とし、原因を直してから再実行する。

### スキルトリガーの仕組み

routing eval の仕組みを理解することで、より良いevalクエリを設計できる。Codex は skill name + description + user query を見て、そのスキルを使うべきかを構造化出力で判定する。これは Claude Code の live `available_skills` trigger 観測ではない。その代わり、`claude -p` を使わず、Codex 環境でのスキル選択判断を安定して回せる。

つまりevalクエリは、スキルを使うかどうかの判断が本当に難しいものにする。明らかな肯定例だけでなく、隣接スキルに任せるべきケース、普通の会話で済むケース、キーワードは似ているが意図が違うケースを必ず混ぜる。

### ステップ4：結果の適用

JSONの出力から `best_description` を取得し、スキルのSKILL.md frontmatterを更新する。変更前後をユーザーに見せてスコアを報告する。

### パッケージングと提示（`present_files` ツールが使える場合のみ）

`present_files` ツールにアクセスできるか確認する。できない場合はこのステップをスキップ。できる場合は、スキルをパッケージングして .skill ファイルをユーザーに提示する：

```bash
python -m scripts.package_skill <path/to/skill-folder>
```

パッケージング後、ユーザーが取得できるよう `.skill` ファイルのパスを案内する。

## Claude.ai 固有の指示

Claude.ai でのコアワークフローは同じ（ドラフト → テスト → レビュー → 改善 → 繰り返し）だが、Claude.ai にはサブエージェントがないため、いくつかのメカニクスが変わる。適応すべき点：

**テストケースの実行**: サブエージェントがないため並列実行は不可。各テストケースについて、スキルのSKILL.mdを読んでから、その指示に従ってテストプロンプトを自分で実行する。1つずつ実行する。独立したサブエージェントほど厳密ではない（スキルを書いた自分が実行するので完全なコンテキストを持っている）が、有用なサニティチェックになる — そして人間のレビューステップがそれを補う。ベースライン実行はスキップ — スキルを使ってリクエストされたタスクを完了するだけ。

**結果のレビュー**: ブラウザを開けない場合（例：Claude.aiのVMにディスプレイがない、リモートサーバー上など）は、ブラウザレビューアを完全にスキップ。代わりに、結果を会話に直接提示する。各テストケースについて、プロンプトと出力を表示する。出力がユーザーが確認する必要のあるファイル（.docxや.xlsxなど）の場合は、ファイルシステムに保存してどこにあるか伝え、ダウンロードして確認できるようにする。インラインでフィードバックを求める：「これはどうですか？変えたいところはありますか？」

**ベンチマーキング**: 定量的ベンチマーキングはスキップ — サブエージェントなしではベースライン比較が意味をなさない。ユーザーからの定性的フィードバックに集中する。

**反復ループ**: 以前と同じ — スキルを改善して、テストケースを再実行して、フィードバックを求める — ただし途中にブラウザレビューアがない。ファイルシステムがあれば、イテレーションディレクトリに結果を整理することはできる。

**description最適化**: `codex exec` が利用できる環境では `run_loop.py` / `run_eval.py` を使って Codex routing eval を実行する。Claude.ai だけで完結する環境ではこの自動最適化をスキップし、手動レビューに切り替える。

**ブラインド比較**: サブエージェントが必要。スキップ。

**パッケージング**: `package_skill.py` スクリプトはPythonとファイルシステムがあれば動作する。Claude.aiでは実行でき、ユーザーは生成された `.skill` ファイルをダウンロードできる。

## Cowork 固有の指示

Coworkにいる場合、知っておくべき主なこと：

- サブエージェントがあるので、メインワークフロー（テストケースの並列起動、ベースライン実行、採点など）は全て動作する。（ただし、タイムアウトで深刻な問題が発生した場合は、テストプロンプトを並列ではなく直列で実行してもよい。）
- ブラウザやディスプレイがないので、evalビューアを生成する際は、サーバーを起動する代わりに `--static <output_path>` を使ってスタンドアロンHTMLファイルを書き出す。その後、ユーザーがクリックしてブラウザでHTMLを開けるリンクを提示する。
- 何らかの理由で、Coworkのセットアップはテスト実行後にevalビューアを生成することをClaudeに思わせない傾向がある。改めて強調する：CoworkにいるときもClaude Codeにいるときも、テスト後は必ずevalビューアを生成してから、自分で入力を評価して修正しようとすること。`generate_review.py` を使って（独自のHTMLを書くのではなく）。大文字で言う：入力を自分で評価する*前に*EVALビューアを生成すること。できるだけ早く人間の目に届けること！
- フィードバックの仕組みが異なる：実行中のサーバーがないので、ビューアの「すべてのレビューを送信」ボタンは `feedback.json` をファイルとしてダウンロードする。そこから読み取ることができる（最初にアクセス許可を求める必要があるかもしれない）。
- パッケージングは動作する — `package_skill.py` はPythonとファイルシステムがあればよい。
- description最適化（`run_loop.py` / `run_eval.py`）はCoworkでも `codex exec` が利用できる場合に実行する。ただし、スキルを完全に完成させてユーザーが良い状態だと同意するまで後回しにすること。
