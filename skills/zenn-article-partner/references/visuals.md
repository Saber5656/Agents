# 図表判断ガイド

記事の骨子を作るときに、図・表・グラフが必要かを判断するための基準。
図表は装飾ではなく、読者が本文だけでは追いにくい関係や差分を短時間で理解するために使う。

## 判断フロー

1. 読者が迷いやすい関係があるか確認する
2. 文章だけだと長くなる説明があるか確認する
3. 数値、順序、比較、依存関係、状態遷移のどれが主役か分類する
4. 必要な図表タイプを 1〜3 個だけ候補にする
5. 図表が不要なら「不要」と理由を明記する

## 図表タイプの選び方

### フロー図

向いている内容:

- 処理手順
- 導入手順
- エラー調査の順番
- 判断分岐

出力例:

```markdown
## 図表の要否
- 必要な図表: フロー図
- 理由: hydration error の調査順を文章だけで追うと読者が迷いやすい
- 候補: 「症状確認 → 再現条件確認 → SSR/CSR差分確認 → 修正 → 再確認」
```

### シーケンス図

向いている内容:

- クライアントとサーバーのやり取り
- API 呼び出し
- 認証フロー
- 非同期処理

### 構成図

向いている内容:

- ツールやサービスの関係
- ディレクトリ構成
- エージェントやプロセスの役割分担
- デプロイ構成

### 比較表

向いている内容:

- Zenn と Qiita の比較
- ライブラリやツールの選定
- 複数案のメリット・デメリット
- 採用判断の根拠

### 判断マトリクス

向いている内容:

- 条件によって選ぶべき手段が変わる
- 読者に意思決定してほしい
- 単なる比較表より「どれを選ぶか」が重要

### グラフ

向いている内容:

- 実行時間
- ビルド時間
- メモリ使用量
- エラー件数
- スコアや計測値の変化

注意:

- 数値データがないならグラフを提案しない
- 推測値でグラフを作らない
- データが足りない場合は「グラフ化するなら必要なデータ」を不足情報に入れる

## 不要と判断してよいケース

- 文章と短いコードブロックだけで十分に伝わる
- 図にしても情報量が増えない
- 読者が見るべき実体がコードやログそのもの
- 図表作成のために未検証の関係を補完する必要がある

## 骨子に入れる標準フォーマット

```markdown
## 図表の要否
- 必要な図表:
- 理由:
- 候補:
- 不足データ:
```

`必要な図表` には `なし` も許可する。
その場合も、なぜ不要かを `理由` に書く。
